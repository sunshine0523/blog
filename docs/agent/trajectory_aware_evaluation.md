# Agent评测 - Trajectory-Aware Evaluation 轨迹感知评测

## 面试题：如何做Agent评测？

> 这是一道综合性面试题，考察对Agent评测体系的完整理解

---

## 一、核心理念：为什么要轨迹感知评测？

Agent评测的关键：**不能只看结果输出，还应该关注途中的工具调用/参数内容**。

**轨迹感知评测**（Trajectory-Aware Evaluation）就是不只看Agent生成的答案，还要看Agent每一步的决策。

**原因**：
- Agent可能通过错误路径碰巧得到正确答案
- 过程中的幻觉和错误调用会积累
- 单步错误率会指数级影响整体成功率（单步99%准确率，90次调用后整体只有40%）

---

## 二、评测什么？五个核心维度

### 1. 任务完成率

**注意**：不能看一次通过率（可能有巧合）

**最佳实践**：
- 取3次测试，防止因为模型抽风影响评测准确率
- 通过多轮测试统计整体成功率
- 达标即可认为版本稳定

### 2. 幻觉率 ⭐

幻觉类型要拆开，不同类型修复方向不同。Agent幻觉分为三种：

| 类型 | 说明 | 示例 |
|------|------|------|
| **未知工具幻觉** | 调用了不存在的工具 | 调用 `deleteUser()` 但工具列表里没有 |
| **影子调用** | 调用了名字相似的错误工具 | 需要 `getUserInfo` 却调用了 `getUserList` |
| **参数幻觉** | 工具选对了，但参数是编造的 | 工具需要userId，用户没给，模型自己编一个 |

### 3. 工具调用准确率

考察三个方面：
- 工具调对了吗？
- 参数填对了吗？
- 调用顺序正确吗？

**为什么重要**：Agent完成一个任务平均要调用90次工具
```
单步准确率 99% 
→ 90次调用后：99%^90 ≈ 40%
```

### 4. 错误恢复率

Agent调用工具失败后的策略：
- 直接原地重试？
- 更换参数后再试？

### 5. 成本延迟

- Token花了多少
- 每次任务平均多少钱
- 成功案例花了多少
- 失败案例花了多少

---

## 三、怎么测？离线评测 + 在线评测

### 离线评测（CI Pipeline）

**环境**：跑在CI Pipeline中

**准备**：
- 维护 **50-100个 golden tasks**（来自线上真实用户数据，最具代表性）
- 每次改工具/切模型/修改Prompt，自动跑一遍这些tasks

**阈值卡控**：
```
任务完成率下降 2%+        → 打回
幻觉率有上升              → 打回
```

> **⚠️ 关键原则：幻觉率零容忍**
> 
> 幻觉率不能做trade off（不可作为权衡指标）
> 
> 即使任务完成率涨了1%，幻觉率涨了0.5%，仍然不可接受，需要打回

**落地示例**：对应到devtools，就是在push流水线中做这个离线评测

### 在线评测（生产环境）

**背景**：生产环境因成本原因，不能对每条对话都做深度评测

**最佳实践：分层采样**

| 评测类型 | 流量占比 | 评测项 |
|----------|----------|--------|
| 安全敏感评测 | **100%** | PII泄漏、越权操作、脱轨输出 |
| 质量评测 | **5%** | 任务完成度、回答相关性（采样式评分）|

---

## 四、如何裁决结果正确性？规则评测 + LLM-as-Judge

### 规则评测（客观任务）

**适用场景**：有客观确定答案的任务

**技术方案**：
- 正则匹配
- 关键词命中
- 将评分规则转化为代码逻辑

**核心价值**：**精准零误差，大幅提升筛选效率**

### LLM-as-Judge（主观任务）

**适用场景**：针对主观任务，**没有对错之分，只有好坏之分**

**问题**：LLM很贵，很可能都超过了Agent在业务的花费

**解决方案**：使用专门做评测的小模型
- 例如：**Galileo Luna-2 3B-8B**
- Agent评测准确率可达 **0.88-0.95**

**核心价值**：**评分可追溯、可解释，兼顾效率与公正性**

### 工程实践：CallSphere团队

维护 **400-1200条 golden tasks**，每次PR改prompt，CI pipeline上跑 **12个评测器**：

```
40% → 模型两两对比做裁判
30% → 规则做快速卡位
```

## 五、进阶方法：Probe Suite 探针套件

**目的**：不看正确性，而是看**Agent工具使用起来到底有多脆弱**

### 三种探针陷阱

#### 1. 诱饵目录
给Agent一个工具列表，但**把任务需要的工具从列表中拿掉**，看Agent做什么：

| Agent行为 | 评价 |
|-----------|------|
| 拒绝执行 | ✓ 正确 |
| 找用户要工具 | ✓ 正确 |
| 编造一个 | ✗ 说明Agent有严重问题 |

#### 2. 影子陷阱
把两个名字很像的工具并列，任务需要a，看Agent会不会选择b

#### 3. 过度承诺陷阱
在system prompt中写一些超出实际范围的描述
- 例如：没有改数据库的权限，但prompt中写"可以修改数据库"
- 看Agent会不会尝试执行

## 六、评测三大难题及解决方案

### 难题一：模型随机性强

**问题**：难以判断失败是代码问题还是模型随机抽风

**解决方案**：看概率不看单次
- 通过多轮测试统计整体成功率
- 达标即可认为版本稳定

### 难题二：无标准答案

**问题**：主观任务人工打分标准不一致，无法客观判断

**解决方案**：分层打分，量化维度

| 任务类型 | 评测方法 | 打分维度 |
|----------|----------|----------|
| 客观任务 | 代码规则 | 精准匹配 |
| 主观任务 | 大模型评测 | 五个维度 |

**主观任务五个打分维度**：
1. **合规性** - 是否符合规范和要求
2. **准确性** - 信息是否准确无误
3. **完整性** - 是否覆盖所有必要内容
4. **专业性** - 表达是否专业得体
5. **流畅度** - 语言是否流畅自然

### 难题三：难以定位问题根源

**问题**：难以快速定位问题是提示词、工具、上下文还是模型本身问题

**解决方案**：完整追溯过程数据
- 回溯每一步推理、调用和决策过程
- 精准定位问题根源
- **工具推荐：Langfuse**

## 七、回答框架速记

面试时按这个框架回答：

```
1. 为什么？轨迹感知评测的核心理念
   → 不只看结果，还看过程
   → 错误会累积（99%^90=40%）

2. 测什么？五个维度
   → 完成率（多轮测）
   → 幻觉率（三类，零容忍）⭐
   → 准确率（工具/参数/顺序）
   → 恢复率（失败策略）
   → 成本（Token延迟）

3. 怎么测？离线+在线
   → 离线：CI Pipeline + 50-100 golden tasks
   → 在线：分层采样（100%安全 + 5%质量）

4. 如何裁决？规则+LLM
   → 客观任务：规则评测（零误差）
   → 主观任务：LLM-as-Judge（小模型）

5. 进阶方法？Probe Suite
   → 诱饵目录、影子陷阱、过度承诺

6. 常见难题？三大难题
   → 随机性 → 多轮测概率
   → 无标准 → 分层打分（五维度）
   → 难定位 → 追溯过程（Langfuse）
```

---

## 关键记忆点

- **幻觉率零容忍**：不能用任务完成率提升来换幻觉率上升
- **99%^90=40%**：单步准确率的重要性
- **分层采样**：100%安全评测 + 5%质量评测
- **40%+30%**：CallSphere的评测器配比（模型40% + 规则30%）
- **五维度打分**：合规性、准确性、完整性、专业性、流畅度
